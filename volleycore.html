Game systems case study

VolleyCore

A Paper and Spigot volleyball system with persistent arenas, teams, lineups, custom display-based ball physics, technique controls, scoring, rotations, a practice bot, and a dedicated resource pack.

Source code Installation Full guide

01 / Problem

Volleyball does not map naturally onto Minecraft's built-in mechanics.

A convincing match needs a controllable ball, predictable contacts, two court sides, serves, scoring, rotations, lineups, and technique-specific player input. A normal mob or dropped item does not provide the visual control or physics model this requires.

The project therefore treats volleyball as its own game runtime layered on top of the server rather than as a collection of disconnected commands.

02 / Constraints

Server-side gameplay with a small, explicit dependency surface.

Paper / Spigot 1.21

The runtime targets modern server APIs and Java 21.

WorldEdit integration

WorldEdit or FAWE selections define and split persistent arena bounds.

Resource-pack visuals

A custom model provides the intended ball and technique item appearance.

Beta status

Core match flow is public while physics and UX remain open to playtesting.

03 / System

Match state, rendering, physics, and player flow are separate systems.

Arenas

Persistent bounds, side detection, preview particles, setup, edit, list, and delete flows.

Ball runtime

Custom physics, hit detection, contact sectors, scale tuning, and display-entity rendering.

Match state

Serve state, scores, sets, side-out rotation, movement rules, and cleanup.

Teams

Creation, invitations, captains, lineup assignment, ready checks, and persistent profiles.

Techniques

Receive, set, attack, block, and serve tools with input tracking and ability-range feedback.

The ball is a dedicated simulation and display system, not a renamed slime with a few event handlers around it.

04 / Product flow

The system supports setup, organized matches, and solo iteration.

Operator setup

Admins create arenas from selections and tune ball scale or physics values in game.

Player onboarding

An in-game guide and English / Russian technique text reduce external setup knowledge.

Match workflow

Teams, captains, lineups, ready state, serve flow, scoring, and world displays form one path.

Practice mode

A side-selectable bot makes the main mechanics testable without a full group of players.

06 / Lessons

What this project demonstrates.

  • Game mechanics become maintainable when rendering, physics, state, and input have clear ownership.
  • Admin setup and player onboarding are part of the system, not documentation afterthoughts.
  • A practice bot is useful engineering infrastructure when multiplayer testing access is limited.
  • Public beta language is more honest than pretending that physics tuning is finished.
